**Real bug found and fixed by testing against the actual database:** every POST
returned 400 ("Invalid input" on `created_at`) even though the row was written
successfully every time — the mock's `insert()` faked `created_at` with JS's
`.toISOString()` (`...Z`), but real PostgREST returns a numeric offset
(`+00:00`) with microsecond precision, which `z.iso.datetime()`'s defaults reject.
The route was silently lying about failure while actually mutating the database —
a real correctness bug, invisible to the fake-mock test suite because the mock's
timestamp format happened to be the one format the naive schema accepted. Fixed
by adding `pgTimestamptz` (`z.iso.datetime({ offset: true, precision: null })`) as
a new shared building block in `src/lib/schema/timestamp.ts`, applying it
everywhere a live timestamp is validated (`provenance.ts`, `knowledge.ts`,
`entities/schema.ts`), and fixing `supabaseMock.ts` to emit the same
offset-style format the real database does, so a fake-mock test would catch this
class of bug in the future instead of masking it. Cleaned up the duplicate/leftover
rows from the buggy runs, then re-ran clean: all four POSTs returned 201. 131/131
tests passing (permanent suite, scratch test removed); `npm run build` clean.

## Task 1, continued — rebuild-from-empty verification

ADR-0001's amendment flagged the baseline as unproven: it was assembled from live
introspection but never actually applied to an empty database. Barak asked for the
cheapest Docker-free way to prove it, and to check whether this CLI version
supports `supabase db reset --linked` first (it does — resets the *linked remote
project itself* using local migration files, no local Docker stack involved).

**Backup before anything destructive.** Queried exact row counts first: beyond the
1 workspace / 1 membership / 4 entities from this session, the live DB held 8 real
deals and everything nested under them (9 documents, 176 data fields, 52 units, 23
messages, 3 notes, 1 offer structure, 4 recommendations, 1 LOI, 4 LOI versions, 5
chat proposals) — accumulated real testing data, not something `db reset --linked`
would touch to fix. Presented the exact inventory and asked before running
anything destructive, per Barak's instruction; he chose to back up the 8 deals
first rather than skip straight to reset. Exported all of it (plus, on his
follow-up, the 9 `deal-documents` storage objects' `storage_path`/name/`deal_id`,
to identify orphans afterward) to a single JSON file — deliberately placed in the
session scratchpad, **not** the repo, since it contains real parsed financials and
document text (Barak's explicit instruction; `supabase/.temp/` was the other
option offered, scratchpad was more unambiguously outside git history).

**`supabase/seed.sql` added** so the workspace + four entities come back
automatically after any reset, rather than needing a manual re-insert — written
idempotently (`on conflict ... do nothing`) against the real operator's Clerk ID,
not fixture/demo data. `[db.seed]` was already `enabled = true` with
`sql_paths = ["./seed.sql"]` in `config.toml`, just no file existed yet.

**Ran `supabase db reset --linked --yes`.** Applied `0001_baseline.sql` →
`0002_workspace_members.sql` → `0003_entities.sql` in order, then `seed.sql`,
against the live project, in one clean pass — no errors.

**Verification results (all three clean):**
1. **Migrations applied cleanly, in order** — confirmed from the reset command's
   own output (`Applying migration 0001_baseline.sql...` → `0002...` → `0003...` →
   `Seeding data from supabase/seed.sql...`).
2. **Rebuilt schema matches the pre-reset inventory exactly.** Table count 18
   (16 original + `workspace_members` + `entities`), all `rls_enabled: true`.
   Re-ran the same verbose `list_tables` / trigger / policy queries used to build
   the baseline and compared against the pre-reset captures: every column, type,
   default, nullability, and foreign key matches; exactly 2 triggers
   (`deals_updated_at`, `deal_data_fields_updated_at` — no `deal_loi_updated_at`,
   confirming that finding wasn't a transcription artifact); 18 RLS policies (one
   per table). Nothing missing. Seed data content also matches exactly: same 4
   entities with correct `formation_state`/`status` per ADR-0006, same real
   `owner_clerk_id`.
3. **`supabase migration list --linked` now shows local and remote in full
   agreement** — `0001`/`0002`/`0003` on both sides, no orphan entries. The reset
   overwrote the remote history table with exactly the 3 local migrations, which
   closed the six-entry (now eight, after `apply_migration`'s two additions)
   mismatch as a side effect, exactly as anticipated.

**Residual, not a defect:** the reset only touches the `public` schema — the 9
files in the `deal-documents` storage bucket were confirmed still present
afterward. They are now orphans (their `deal_documents` rows are gone). The
backup's `storage_objects` section records exactly which files these are and
which `deal_id`/`deal_document_id` they used to belong to, for whenever that
cleanup happens.

**Exit criterion 1 ("a new table can be added, applied, and rolled back by
tooling") is now met**, including the part that wasn't demonstrated in the first
pass: "rolled back" is satisfied by `db reset --linked` itself — the same tooling
that proved the baseline also proves the full migration set is reproducible from
nothing, which is the substance of what a rollback guarantee is for here (Supabase
CLI migrations are forward-only; reset-and-replay is the mechanism, not a
`down.sql` per migration).
