## Task 1 — Counterparties and documents

### ADR-0009 (required by PHASE-1 Task 1 explicitly)
Wrote `docs/decisions/0009-two-document-tables-temporarily.md`: `documents` is a new
table, separate from `deal_documents`, which stays untouched this phase. Recorded the
duplication and an intended sunset (fold `deal_documents` into `documents` once
`deals.property_id` is populated on close), matching the same deferred-merge shape as
ADR-0007's `crm_contacts`/`buyers` → `counterparty`.

### Migrations
- `0004_counterparties.sql` — `kind` validated at the Zod boundary only, no DB check
  constraint, matching the existing `entities.status`/`entity_type` convention.
- `0005_documents.sql` — `property_id`/`unit_id`/`lease_id` are plain nullable `uuid`
  columns with no FK yet (those tables don't exist until Tasks 2-4); FK constraints
  land in the migration that creates each target table. `unique(workspace_id, sha256)`
  is the actual dedup backstop. Also creates the `documents` storage bucket via a
  `storage.buckets` insert in the same migration — checked its exact column
  requirements first (`id`, `name`, `type` required; everything else defaulted) rather
  than guessing, and mirrored `deal-documents`' config (private, 50MB, same MIME
  list) exactly rather than approximating it.

### Domain modules + routes
`src/domains/counterparties/{schema,handlers}.ts`, `src/domains/documents/{schema,handlers}.ts`,
thin routes at `src/app/api/counterparties/route.ts` and `src/app/api/documents/route.ts`,
both via `withWorkspace()` — same reference pattern as `entities` from Phase 0.

`documents`' create path is metadata-only at upload time (`name`, `file_type`,
`source`, `counterparty_id`, `deal_id`) — `raw_text`, `parse_confidence`,
`parsed_at`, `property_id`, `unit_id`, `lease_id` are populated later by the parsing
pipeline (Task 5) and by Tasks 2-4 respectively, not guessed at now.

Duplicate detection: an explicit `maybeSingle()` pre-check on `(workspace_id, sha256)`
gives a clean 409, with the DB's unique constraint as the actual backstop against the
check-then-insert race (`error.code === "23505"` path).

### Three real bugs found running the tests, all in `supabaseMock.ts`, not app code
The fake mock's `insert()` only backfilled `id` and `created_at` as Postgres defaults.
Two more surfaced today:
1. **`updated_at` wasn't defaulted at all.** `counterparties` has both `created_at`
   and `updated_at` (`entities`, the only prior table using this mock, has only
   `created_at`), so this never showed up before. Response validation against
   `counterpartySchema` correctly failed until the mock started defaulting both.
2. **Columns not present in the insert payload just don't exist on the mock's
   returned row**, whereas real Postgres always returns every column (set value or
   explicit `null`). `documents`' create path only sends a subset of columns by
   design (the rest come later) — the mock's `insert()` doesn't know the full column
   set of any table, so it can't backfill the rest the way Postgres implicitly does.
   Fixed by making the handler explicit: `createDocument` now passes
   `raw_text: null, parse_confidence: null, parse_warnings: [], parsed_at: null,
   property_id: null, unit_id: null, lease_id: null` at insert time, rather than
   relying on the DB (or the mock) to fill them in silently. This is the same lesson
   as the `pgTimestamptz` bug from Phase 0 Task 5: don't trust implicit backend
   behavior to match what the schema expects — be explicit at the call site.

A third, unrelated to the mock: **jsdom's `Request`/`FormData`/`File` do not
correctly round-trip a multipart body** — an uploaded file's `name` came back as the
literal string `"blob"`, and `instanceof File` was `false` against the test file's
own global `File` (jsdom runs its own realm with its own File class). Not a route
bug — Next.js route handlers run on Node's native fetch (undici) in production,
which doesn't have this gap. Fixed by adding `@vitest-environment node` to
`documents/route.test.ts` only (it tests server logic, needs no DOM) rather than
changing the project-wide jsdom default, which every other test still needs.

## Migration tooling, settled before Task 2

Barak flagged that the migration-history mismatch had recurred (same shape as ADR-0001's
first amendment) and asked to settle the standard command now, since a reset stops being
a cheap fix once Task 2 backfills real portfolio data.

Answered both questions empirically rather than from memory:
1. **Does `supabase db push --linked` apply local migration files directly, keyed by
   filename?** Yes — confirmed via `--dry-run`, which also proved it *refuses* to run
   while local/remote disagree (`LegacyDbPushMissingLocalError`), and its own error message
   supplies the exact repair command needed.
2. **Does `supabase migration repair` align bookkeeping without a reset?** Yes — ran
   `migration repair --status reverted 20260812104347 20260812104402 --linked` (the two
   stray `apply_migration` timestamps) then
   `migration repair --status applied 0004 0005 --linked` (the two local files whose SQL
   had already run — repair only edits the history table, does not re-run or undo
   anything). `db push --linked --dry-run` then reported `"upToDate": true`.

**`supabase db push --linked` (also `npm run db:migrate`, corrected from a bare
`supabase migration up` that defaulted to a local Docker target and had never actually
been exercised) is now the documented standard path in `CLAUDE.md`.** `apply_migration`
remains a legitimate escape hatch, but any session that uses it must immediately run the
same repair sequence before ending — documented so this isn't rediscovered a third time.
Added as ADR-0001's Amendment 3 (dated, per the "decision is immutable, mechanism
corrections are dated amendments" rule ADR-0005 established).
